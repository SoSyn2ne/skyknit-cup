# Milestone 1 검증 기록

> 상태: **완료 검증됨**
>
> 검증일: 2026-07-10

## 결과

- 60Hz 고정 스텝의 자동 전진 비행과 상승, 하강, 선회, 시각적 뱅크를 구현했다.
- 용량 100의 부스트에 40/s 소비, 0.5초 회복 지연, 20/s 회복, 1.6배 속도를 적용했다.
- W/S와 방향키 상하, A/D와 방향키 좌우, Shift와 Space 입력을 지원한다.
- 짧은 키 탭도 다음 고정 스텝에서 한 번 소비해 렌더 프레임 사이의 입력 유실을 막았다.
- world-up을 유지하는 임계 감쇠 추적 카메라와 55~63도 부스트 FOV 추종을 구현했다.
- 임시 주홍 드래곤, 금빛 기준 관문, 두 가닥의 밝은 바람실을 전체 화면 장면에 배치했다.
- M0의 강제 WebGL 실패, 한국어 안내, 같은 탭 재시도 복구를 보존했다.
- Blender 원본, GLB, 컨셉 시트와 M2 이후 범위는 변경하지 않았다.

## 테스트 우선 증거

1. `fixedStep.test.ts`, `flightModel.test.ts`, `KeyboardInput.test.ts`를 구현보다 먼저 작성했다.
2. 첫 M1 `npm test`에서 세 구현 모듈이 없어 3개 스위트가 실패하고 M0의 30개 테스트만 통과했다.
3. 최소 구현 뒤 5개 파일, 55개 테스트가 통과했다.
4. 실제 브라우저의 빠른 키 탭이 프레임 사이에서 유실되는 문제를 확인한 뒤 실패 테스트 2개를 추가했다.
5. `consumeInput` 부재로 두 테스트가 RED인 것을 확인하고 한 스텝 입력 버퍼를 구현했다.
6. 브라우저 이벤트 리스너의 빠른 탭, blur, hidden 정리까지 추가해 최종 5개 파일, 59개 테스트로 고정했다.

최종 테스트는 M0의 레이스 상태와 관문 기하를 포함하며 다음 M1 계약을 직접 검증한다.

- 1초 중립 비행 거리 24 units
- 최대 이동 피치 22도, 최대 시각 피치 18도, 최대 뱅크 30도
- yaw 1.4 rad/s와 뱅크의 이동 방향 비개입
- 상승 최대 15% 감속과 하강 최대 20% 가속
- 부스트 40/s 소비, 0.5초 지연, 20/s 회복, 상한과 고갈 상태
- 1초 호스트 hitch를 최대 0.1초, 즉 6개 스텝으로 제한
- 키 해제와 빠른 탭, `window.blur`, hidden `visibilitychange` 입력 정리

## 결정성

10초 입력 계약을 모든 cadence에서 동일한 600개 고정 스텝으로 소비했다.

| 호스트 cadence | 호스트 프레임 | 시뮬레이션 스텝 | 거리/부스트/방향 오차 |
| --- | ---: | ---: | --- |
| 30fps | 300 | 600 | 기준 허용치 통과 |
| 60fps | 600 | 600 | 기준 |
| 120fps | 1,200 | 600 | 기준 허용치 통과 |
| `[1/20, 1/120, 1/45, 1/90]` | 437 | 600 | 기준 허용치 통과 |

60fps 기준 최종 heading은 `0.7rad`, 부스트 잔량은 `50`이다. 모든 cadence의 이동 거리와 부스트 잔량은 2% 이내, 최종 방향은 1도 이내이며 현재 테스트는 이동 거리가 소수점 9자리까지 일치함을 추가로 고정한다.

## 실제 브라우저 조작

Codex 인앱 브라우저에서 실제 키press로 `31.3초` 동안 W, S, D, A, Shift, Space를 순서대로 조작했다. 자동화 API가 분리된 keydown/keyup을 제공하지 않아 빠른 반복 탭으로 검증했으며, 한 스텝 입력 버퍼가 각 실제 탭을 시뮬레이션에 전달했다.

| 검증 | 관측값 |
| --- | --- |
| W 상승 | pitch `+0.1134rad`, 고도 상승 |
| S 하강 | pitch `-0.1198rad`, 고도 하강 |
| D 우선회 | heading `+1.4rad`, bank `-0.1818rad` |
| A 좌선회 | heading이 거의 0으로 복귀, bank `+0.1497rad` |
| Shift 부스트 | 잔량 `100 -> 60`, FOV `55 -> 57.71` |
| Space 부스트 | 속도 `24 -> 38.4`, FOV 최대 `58.38`, 잔량 최저 `22.67` |
| 전체 이동 | `780.22 units` |
| 카메라 | world-up 내적 최저 `0.965`, 뒤집힘 없음 |
| 프레이밍 | 모든 샘플에서 드래곤과 관문이 NDC 안에 유지됨 |
| 종료 입력 | pitch/yaw/boost 모두 0, 입력 고착 없음 |
| 브라우저 로그 | warning 0, error 0 |

브라우저의 탭 생성만으로는 실제 `visibilitychange`가 발생하지 않아 blur/hidden은 `EventTarget` 기반 실제 리스너 테스트로 검증했다. 두 이벤트 모두 held 입력과 버퍼 입력을 지우며 카운터와 원인을 기록한다.

| `1280x720` | 통과 | 없음 | 모두 표시 | 2,936 |

- 각 캔버스의 CSS 경계가 뷰포트와 정확히 일치했고 문서 스크롤이 없었다.
- 1.1초 간격 캡처의 SHA-256이 다섯 크기 모두 달랐다.
- 4픽셀 간격 표본에서 각 캡처는 배경 외 픽셀 794개 이상과 고유 색상 562개 이상을 포함했다.
- 드래곤과 관문은 다섯 크기 모두 화면 안에 있었고 바람실 개수는 2개였다.
- 최종 시각 판정은 `94/100`, `pass`다.
- 콘솔 warning, error, 처리되지 않은 rejection은 관측되지 않았다.

## M0 회귀와 프로덕션 경계

- `?forceWebglFailure=1`에서 캔버스가 생성되지 않고 한국어 `alert`와 포커스된 `다시 시도` 버튼이 표시됐다.
- 다시 시도 뒤 실패 쿼리가 제거되고 정상 캔버스가 정확히 하나 생성됐다.
- 실패와 복구 경로 모두 브라우저 warning과 error가 0개였다.
- 프로덕션 `dist`에는 앱 고유 외부 표면인 `forceWebglFailure`, `__DRAGON_RACE_TEST__`, `flightDebug`, `mirrorDebugSnapshot`과 진단 payload 키 `cameraFov`, `cameraUpDotWorldUp`, `inputClears`가 남지 않는다.
- RendererSession과 FlightSandbox의 개발 전용 컨텍스트 손실 트리거·스냅샷 구현은 프로덕션 객체에서 제거된다.
- 입력 클래스의 내부 `snapshot`/`debugSnapshot` 메서드명과 Three.js의 `loseContext`/`WEBGL_lose_context` 지원 코드는 배포 번들에 존재할 수 있다. 외부 글로벌 훅으로 노출되지는 않으며, 실제 컨텍스트 손실을 안내 화면으로 전환하는 프로덕션 리스너는 의도적으로 유지한다.

## 단순화와 남은 위험

- 비행, 고정 스텝, 입력 상태는 Three.js와 분리된 순수 로직으로 유지했다.
- 뱅크는 렌더 자세에만 적용하고 이동 방향에는 사용하지 않는다.
- 기준 관문은 레이스 규칙 없이 앞쪽에 재배치되는 시각 참조물 하나로 유지했다.
- 바람실은 별도 효과 라이브러리 없이 두 개의 동적 선 지오메트리만 사용한다.
- 실제 드래곤 리그, 세계, 장애물, HUD, 터치, 타이머와 관문 순서는 각각 M2~M4 범위로 남겼다.
- 자동화 환경에서는 물리 키를 연속으로 누른 상태의 OS 입력을 재현하지 못했다. 실제 반복 키press, 입력 이벤트 테스트, 31.3초 런타임 수치로 교차 검증했으며 최초 외부 플레이테스트에서 연속 홀드 감각을 다시 확인한다.
- Three.js가 포함된 단일 JS 청크는 Vite 기본 500KB 경고를 유지한다. 초기 전송 예산에는 여유가 있고 코드 분할은 실제 로딩 병목이 측정될 때 판단한다.
- 절차 장면은 현재 M1 규모에서 안정적이지만 고정 스텝마다 임시 `Vector3`를 생성한다. M3에서 구름·장애물을 확장하기 전에 scratch 벡터 재사용 여부를 프로파일링한다.
